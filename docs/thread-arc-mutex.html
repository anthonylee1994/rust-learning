Rust: thread, Arc and Mutex

How to run work on several threads and share data between them safely. The demo code below was compiled and run for real, and the output shown is what it printed. Then you write six exercises yourself in src/bin/practice21.rs to practice26.rs.

Roadmap

Mental model (TypeScript / Rails): Node runs your JS on one thread, so two callbacks never touch a variable at the same instant. Rails mostly dodges the problem with separate processes, and Ruby's GVL protects you inside one process. Rust has real threads running at the same time with no global lock, so the compiler is the one that stops data races. thread starts the work, Mutex makes sure one thread at a time touches the data, and Arc lets many threads own that data.
Level Concept Problem it solves
1 thread::spawn and join Run work in the background and wait for it
2 move closures and return values Give a thread its own data and get a result back
3 Mutex<T> Only one thread may read or write the data at a time
4 Arc<T> Many owners of one value, across threads
5 Arc<Mutex<T>> Many threads that all change the same value
6 Lock scope, poisoning, deadlock Use the combo without making it slow or stuck

Level 1thread::spawn and join

thread::spawn takes a closure and runs it on a new thread right away. It returns a JoinHandle. Calling .join() on it means "wait until that thread is done". Think of it as await for a thread: without it, main may end first and kill the worker.

demo 1: spawn and join

use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("worker: step {}", i);
            thread::sleep(Duration::from_millis(10));
        }
    });

    handle.join().unwrap();
    println!("main: worker finished");
}
worker: step 1
worker: step 2
worker: step 3
main: worker finished

What to notice

  • join() returns a Result. It is Err if the thread panicked. The panic does not crash main, you get to decide. Here we unwrap because this is a learning project.
  • The output order above is stable only because we join before the last println!. If two threads print at the same time, the order is not fixed and can change on every run.
  • Forget the join and the program may exit before the worker prints anything. That is a classic first surprise.

Level 2move closures and return values

A new thread may live longer than the function that created it, so it cannot borrow local variables. It must own what it uses. The move keyword in front of the closure moves the variables in. The closure's return value comes back through join().

demo 2: move in, result out

use std::thread;

fn main() {
    let data = vec![1, 2, 3, 4, 5];

    // `move` hands ownership of `data` to the new thread.
    let handle = thread::spawn(move || data.iter().sum::<i32>());
    println!("sum from worker: {}", handle.join().unwrap());

    let mut handles = vec![];
    for i in 1..=4 {
        handles.push(thread::spawn(move || i * i));
    }

    let squares: Vec<i32> = handles.into_iter().map(|h| h.join().unwrap()).collect();
    println!("squares: {:?}", squares);
}
sum from worker: 15
squares: [1, 4, 9, 16]

The error you will hit first

Remove move and the compiler stops you:

let data = vec![1, 2, 3];
let handle = thread::spawn(|| {
    println!("{:?}", data);
});
error[E0373]: closure may outlive the current function, but it borrows `data`,
              which is owned by the current function
help: to force the closure to take ownership of `data` (and any other
      referenced variables), use the `move` keyword
  • Why: if main dropped data while the thread still ran, the thread would read freed memory. Rust refuses at compile time. In TypeScript this is just a possible bug, in Rust it is an error.
  • Result: after move, data belongs to the thread. main cannot use it any more (Round 1 ownership, same rule).
  • Loop trick: for i in 1..=4 with move gives each thread its own copy of i, because integers are Copy.
  • Collect handles first, join later. Joining inside the spawn loop would run the threads one by one, which defeats the point.

Level 3Mutex: one thread at a time

Mutex means "mutual exclusion". It is a box with one key. To touch the value inside you must call .lock(), which waits for the key and gives you a guard. When the guard is dropped, the key goes back. Ruby has Mutex#synchronize, but in Ruby the data lives outside the mutex and you can forget to lock. In Rust the data lives inside the Mutex, so forgetting is impossible.

demo 3: Mutex on one thread (to learn the API)

use std::sync::Mutex;

fn main() {
    let counter = Mutex::new(0);

    {
        let mut guard = counter.lock().unwrap();
        *guard += 1;
        *guard += 1;
    } // guard dropped here, lock released

    println!("counter = {}", *counter.lock().unwrap());
}
counter = 2

What to notice

  • lock() returns a Result (see "poisoning" in Level 6), so we unwrap() it. The guard acts like a &mut i32, so we write *guard += 1.
  • Note let counter is not mut. A Mutex lets you change the inside through a shared reference. This is called interior mutability: the lock, not mut, is the safety check.
  • The guard is released at the end of the scope (RAII, like a Ruby ensure that runs for you). The inner { } block makes that moment explicit.

Level 4Arc: many owners across threads

Ownership says one owner per value. But several threads may need the same data, and a thread needs to own what it holds (Level 2). Arc solves this: it is a pointer with a counter. Each Arc::clone adds one owner. The value is freed when the last owner goes away. Arc stands for "atomically reference counted".

demo 4: watch the counter

use std::sync::Arc;

fn main() {
    let name = Arc::new(String::from("shared text"));
    println!("count = {}", Arc::strong_count(&name));

    let other = Arc::clone(&name);
    println!("count after clone = {}", Arc::strong_count(&name));

    {
        let _third = Arc::clone(&name);
        println!("count in inner scope = {}", Arc::strong_count(&name));
    }

    println!("count after scope = {}", Arc::strong_count(&name));
    println!("other sees: {}", other);
}
count = 1
count after clone = 2
count in inner scope = 3
count after scope = 2
other sees: shared text

What to notice

  • Arc::clone(&name) copies only the pointer and bumps the count. The String is not copied. This is the "clone only when two owners are really needed" case from your notes, and it is cheap.
  • Prefer writing Arc::clone(&x) over x.clone(), so a reader sees at once that this is a cheap pointer copy.
  • The inner scope shows the count going back down when _third is dropped. There is no garbage collector pause: it is counted exactly.
  • Alone, Arc is read-only. You cannot change the value inside. For that you need Level 5.

Why not Rc?

Rc is the same idea, but its counter is not thread safe, so it is faster. Rust knows this and refuses to send an Rc to a thread: 

let data = Rc::new(5);
let handle = thread::spawn(move || {
    println!("{}", data);
});
error[E0277]: `Rc<i32>` cannot be sent between threads safely
  = help: within `{closure}`, the trait `Send` is not implemented for `Rc<i32>`
Send in one line: Send is a marker trait meaning "this type is safe to move to another thread". thread::spawn requires it. You never write it yourself, the compiler works it out. Rule: in threads use Arc, in single-threaded code use Rc.

Level 5Arc<Mutex<T>>: the standard combo

Put them together. Arc gives every thread ownership, Mutex lets them change the value one at a time. This is the Rust version of "a shared counter protected by a lock".

demo 5: 8 threads, each adds 1000

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..8 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                *counter.lock().unwrap() += 1;
            }
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("final counter = {}", *counter.lock().unwrap());
}
final counter = 8000

What to notice

  • The result is always 8000. Without the lock, two threads can read the same number, both add one, and write back, losing an update. That is a data race, and Rust will not compile the unprotected version.
  • let counter = Arc::clone(&counter); inside the loop is shadowing. Each thread gets its own Arc pointer, and the move closure takes that one. The outer counter stays in main.
  • *counter.lock().unwrap() += 1 is a one-liner: lock, change, and the guard is dropped at the end of the statement.

The error that shows why Arc is needed

Try the same loop with a bare Mutex and no Arc: 

error[E0382]: use of moved value: `counter`
  |     let counter = Mutex::new(0);
  |         ------- move occurs because `counter` has type `Mutex<i32>`,
  |                 which does not implement the `Copy` trait
  |     for _ in 0..2 {
  |     ------------- inside of this loop
  |         handles.push(thread::spawn(move || {
  |                                    ^^^^^^^ value moved into closure here,
  |                                            in previous iteration of loop

The first thread takes the only Mutex, so the second loop round has nothing to give. Arc is how you hand out several owners.

Level 6keep the lock short

While a thread holds the guard, every other thread that calls lock() waits. So the goal is: do the slow work outside, hold the lock only for the quick update.

demo 6: collect results from threads

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let results = Arc::new(Mutex::new(Vec::new()));
    let mut handles = vec![];

    for id in 1..=4 {
        let results = Arc::clone(&results);
        handles.push(thread::spawn(move || {
            // Do the slow work first, without holding the lock.
            let value = id * 10;

            // Hold the lock only for the short push.
            let mut list = results.lock().unwrap();
            list.push((id, value));
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    let mut list = results.lock().unwrap();
    list.sort(); // thread order is not fixed, so sort before printing
    println!("{:?}", *list);
}
[(1, 10), (2, 20), (3, 30), (4, 40)]

What to notice

  • value is computed before lock(). If that line were a slow network call, the threads would still run in parallel.
  • The threads push in any order, so the code sort()s before printing. Never depend on thread order.
  • Want to release early inside a long function? Use an inner { } block or drop(guard).

Two traps

Trap What happens How to avoid
Deadlock A thread locks the same Mutex twice without dropping the first guard, or two threads lock A and B in opposite order. Everything hangs, with no error. Hold one lock at a time, keep scopes small, lock in the same order everywhere
Poisoning A thread panics while holding the guard. The next lock() returns Err, to warn you the data may be half-updated. That is why lock() returns a Result. unwrap() is fine for exercises. Real code decides whether to recover or crash.
Not covered yet (good for later rounds): RwLock (many readers or one writer), mpsc::channel (send messages between threads instead of sharing data, often cleaner than a lock), thread::scope (borrow locals without move and Arc), and async. Master this page first.

Exercises

Exercise 1spawn and join practice21.rs

  • Spawn 3 threads in a loop. Thread i prints hello from thread i.
  • Keep every JoinHandle in a Vec, then join them all.
  • After the joins, print all done from main.

Expected: three hello lines in any order, then all done last. Run it a few times and see if the order changes.

Hint

Use for i in 1..=3 and move ||. If you join inside the spawn loop, the lines come out in a fixed order but the threads are not running together. Why?

Exercise 2return values practice22.rs

  • Make a Vec<u32> of 1..=100.
  • Split it into 4 chunks of 25. Give each chunk to its own thread, which returns the sum of its chunk.
  • In main, join all threads, print each partial sum, then print the total.

Expected: partial sums 325, 950, 1575, 2200, and total 5050.

Hint

numbers.chunks(25) gives borrowed slices, and a thread cannot borrow (Level 2). Turn each slice into an owned Vec with .to_vec() before spawn. Joining in order keeps the partial sums in order.

Exercise 3fix 3 compile errors practice23.rs

Make one file with three small broken programs, one per function. Run each one on its own, read the whole error, then fix it.

  • fn a(): a thread uses a Vec without move.
  • fn b(): a thread uses an Rc.
  • fn c(): a Mutex is moved into a thread inside a loop, with no Arc.

Expected: before the fix you can name the error code and say why it happens in one sentence. After the fix all three print something.

The three codes are E0373, E0277 and E0382, which are exactly the three errors on this page. Comment out two functions in main so only one error shows at a time.

Exercise 4watch the Arc counter practice24.rs

  • Create Arc::new(vec![1, 2, 3]) and print Arc::strong_count (expect 1).
  • Spawn 3 threads, each with its own Arc::clone. Each thread prints the sum of the vec.
  • Join all threads, then print the count again.

Expected: count is 1 at the start and 1 at the end, and three lines with sum 6 in between.

Hint

Do not print the count while threads run, because it changes as threads finish and the result is not fixed. Why is it back to 1 after join? Think about what happens to a closure when its thread ends.

Exercise 5bank account practice25.rs

  • Shared balance: Arc<Mutex<i64>>, starting at 100.
  • 5 threads each deposit 10.
  • 3 threads each withdraw 20, but only if the balance is at least 20. Otherwise print insufficient funds.
  • Join everything and print the final balance.

Expected: final balance 90 (100 + 50 - 60), on every run.

Hint

The check and the withdraw must happen under the same guard. If you lock to check, release, then lock again to subtract, another thread can sneak in between. Store the guard in a variable: let mut balance = account.lock().unwrap();

Exercise 6parallel word count practice26.rs

  • Shared map: Arc<Mutex<HashMap<String, usize>>>.
  • Three lines of text: "a b a", "b c", "a c c". One thread per line, each counting its words into the shared map.
  • After joining, collect the map into a Vec, sort by word, and print one word: count per line.

Expected: a: 3, b: 2, c: 3, in that order.

Hint

This is practice17 (entry + or_insert) inside a lock. Lock once per word, or lock once per line and hold the guard for the whole loop. Which one is better, and which one is more obviously correct? Convert &str to String for the key. Sort before printing, because thread order is random.
